BSP patch: RTL8211F link-speed detection
========================================

File:
  <bsp>/ps7_cortexa9_1/libsrc/lwip211_v1_0/src/contrib/ports/xilinx/netif/
  xemacpsif_physpeed.c

Function: get_Realtek_phy_speed()

Symptom
-------
The PHY negotiates 100 Mbit and the link LED is on, but the MAC receives
nothing and the board never answers ARP. Reading the registers shows:

  NWCFG         = 0x011F20C2   speed bit clear -> MAC left at its 10 Mbit reset default
  GEM0_CLK_CTRL = 0x00100801   DIVISOR1 = 1 -> TX clock still at the ps7_init 1000 Mbit setting

Cause
-----
The function ends with

    XEmacPs_PhyRead(xemacpsp, phy_addr, IEEE_SPECIFIC_STATUS_REG, &status_speed);
    if (status_speed & 0x400) { ... }
    return XST_FAILURE;

IEEE_SPECIFIC_STATUS_REG is register 0x11. That is the speed status register on
an RTL8211E, but on an RTL8211F it reads back 0x0000, so the test fails and the
function returns XST_FAILURE, which is 1. The caller then does

    SetUpSLCRDivisors(base, 1);              -> no matching case, clock untouched
    XEmacPs_SetOperatingSpeed(emac, 1);      -> default: return, NWCFG untouched

Neither reports an error, so the MAC is silently left misconfigured.

An RTL8211F keeps link status in register 0x1A of page 0xA43:

  bit 2      link up
  bit 3      duplex
  bits [5:4] speed: 00 = 10, 01 = 100, 10 = 1000

Measured on this board: 0x301E -> link up, full duplex, 100 Mbit.

Patch
-----
Insert before the closing "return XST_FAILURE;" of get_Realtek_phy_speed():

	/* An RTL8211F reports link speed in register 0x1A of page 0xA43, not in the
	 * register 0x11 read above - that one reads back as 0x0000. Without this the
	 * function returns XST_FAILURE, both SetUpSLCRDivisors() and
	 * XEmacPs_SetOperatingSpeed() silently ignore that value, and the MAC is
	 * left at its 10 Mbit reset default while the PHY runs at 100. The symptom
	 * is a healthy link with every receive counter stuck at zero. */
	{
		u16_t phy_id_lo;

		XEmacPs_PhyRead(xemacpsp, phy_addr, 3, &phy_id_lo);
		if ((phy_id_lo & 0xFFFF) == 0xC916) {
			u16_t physr;

			XEmacPs_PhyWrite(xemacpsp, phy_addr, 0x1F, 0x0A43);
			XEmacPs_PhyRead(xemacpsp, phy_addr, 0x1A, &physr);
			XEmacPs_PhyWrite(xemacpsp, phy_addr, 0x1F, 0x0000);

			if (physr & 0x0004) {           /* link up */
				switch ((physr >> 4) & 0x3) {
				case 0: return 10;
				case 1: return 100;
				case 2: return 1000;
				default: break;
				}
			}
		}
	}

After the patch
---------------
  NWCFG         = 0x011F20C3   100 Mbit
  GEM0_CLK_CTRL = 0x00500801   DIVISOR1 = 5, TX clock 25 MHz

and the receive path works end to end - lwIP's arp_table picks up the peer:

  0x1020033C = 6401A8C0   192.168.1.100
  0x10200344 = C9A71454   54:14:A7:C9:96:FD
  0x1020034C = 00000002   ETHARP_STATE_STABLE

Note
----
The patch lives in generated BSP source and is lost whenever SDK regenerates the
board support package. Re-apply it after any BSP regeneration.

Still open: transmit never reaches the peer
------------------------------------------

Board: Artemis Karia StarLite, ETH-PS port, RTL8211F-CG at MDIO address 1.
Peer: a USB 2.0 100 Mbit adapter on the host, direct cable, static addressing
(board 192.168.1.10, host 192.168.1.100).

Verified working
  PHY link          BMSR 0x79AD - link up, autonegotiation complete
  PHY speed         page 0xA43 reg 0x1A = 0x301E - 100 Mbit, full duplex
  MAC speed         NWCFG 0x011F20C3, GEM0_CLK_CTRL 0x00500801 (after the patch)
  Receive path      MAC counts broadcast frames, and lwIP's arp_table holds the
                    host with ETHARP_STATE_STABLE, so frames reach the stack
  netif state       flags 0x0F = UP | BROADCAST | LINK_UP | ETHARP
  Peer MAC          lwIP learned 54:14:A7:C9:96:FD, which is the host adapter
  Analog transmit   autonegotiation completing proves the PHY drives the media

Verified correct against the board schematic (sheets 3, 5, 15)
  VCCO_MIO1_501 = 1.8 V, DVDDRG on the PHY = 1.8 V - levels match
  MIO16 = GTX_CLK, MIO17..20 = TXD0..3, MIO21 = TX_EN,
  MIO22 = RX_CLK, MIO23..26 = RXD0..3, MIO27 = RX_DV - the standard mapping
  MIO52/53 = MDC/MDIO, and MDIO works
  Boot straps: MIO[8] = 1 -> MIO bank 1 at 1.8 V

Tried without effect
  Cache coherency. Xil_DCacheFlushRange() in the standalone BSP wraps its L2
  clean in #ifndef USE_AMP, so on CPU1 only L1 is flushed and a frame handed to
  the EMAC can still be dirty in L2 while the DMA reads stale DDR. On Zynq the
  GEM reaches DDR through the central interconnect and does not snoop L2, so
  this looked like an exact fit for "transmit broken, receive fine". It is a
  real hazard for any DMA driven from an AMP slave core and worth knowing about,
  but it is not this bug: disabling L2 entirely changed nothing, and neither did
  marking every buffer lwIP owns (.bss, heap, stack above 0x10100000)
  non-cacheable so no cache sits between the CPU and DDR at all.
  PHY TX delay on (page 0xD08 reg 0x11 bit 8), with and without renegotiation
  Fast slew rate on MIO 16..27 (the PS configuration leaves all twelve on slow,
  which every Xilinx reference design sets to fast - worth fixing regardless)
  Promiscuous mode

Inconclusive
  BMCR bit 14 loopback on this PHY does not isolate the receive path: with it set
  the MAC still receives the host's frames. A first reading of that test suggested
  the RGMII transmit path was proven good; it was not - the frames counted were
  ordinary host traffic. Repeated with promiscuous mode on and every one of the
  fourteen receive buffers held a frame from the host, none with the board's own
  source address, so the test says nothing either way about MAC -> PHY transmit.

So the host never sees a frame from the board even though every stage that can be
observed from software is healthy.


The measurement that changed the answer
---------------------------------------

The GEM statistics registers are cleared by reading them. Every earlier reading
of them was therefore a delta since the last read, not a total, which is what
made them look inconsistent. Clearing them first and then measuring one window
gives a clean picture. Over the same 20 seconds, with the link up at 100 Mbit:

  board transmitted     54 frames, 13,896 octets, no underruns, no collisions,
                        no carrier sense errors
  board received        19 frames, 6,292 octets, no FCS, symbol, alignment,
                        overrun or resource errors
  host received         0 bytes, 0 packets, 0 errors
  host transmitted      5,866 bytes

Then the whole transmit path was replaced: GEM1 brought out through EMIO to the
second PHY on the PL side of the board - different pins, different bank,
different I/O voltage, different PHY chip, different jack (see ../pl_eth). It
came up, the driver found the PHY, frames went out, and the host still saw
nothing. Two independent paths cannot fail the same way for the same reason.

What the host's own counters say
--------------------------------

Both Ethernet adapters on this laptop have lifetime receive counters of zero:

  USB2.0 Ethernet Adapter               RxBytes 0        TxBytes 13,248
  Realtek PCIe GbE Family Controller    RxBytes 0        TxBytes 217,126
  Intel Wi-Fi 6E AX211                  RxBytes 56,865,439

Not zero for this window - zero since the interface came up, from anything at
all. The Wi-Fi figure is there to show the counter itself works. And four
third-party NDIS filters are bound to the Ethernet interface, two of them VPN
packet filters:

  ExpressVPN Packet Filter          enabled
  WireSock VPN Client Filter        enabled
  VirtualBox NDIS6 Bridged          enabled
  Npcap Packet Driver               enabled

So the evidence now points away from the board. The board transmits; nothing on
this host has ever received an Ethernet frame.

The test that settles it needs no board at all: put the host's Ethernet on a
router and see whether it picks up an address. If it stays on 169.254.x.x, the
receive path on this machine is broken and no amount of work on the board will
change it - start by disabling those two VPN filters.
